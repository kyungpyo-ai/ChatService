## 0. 현재 레포 상태와의 관계

이 저장소는 [nextjs-supabase-starter-kit](https://github.com/kyungpyo-ai/nextjs-supabase-starter-kit)을 베이스라인으로 시작했으며, 아래 기능은 **이미 구현되어 있다**. 후속 문서 작성 및 개발 시 중복 설계하지 않는다.

- 이메일 회원가입/로그인 + OAuth(구글 등) 콜백 구조 (`app/auth/*`)
- 최초 OAuth 로그인 시 닉네임 설정 플로우 (`app/auth/setup-profile`)
- `profiles` 테이블(닉네임, 아바타, 이메일 등) + RLS + 회원가입 트리거
- 인증 미들웨어를 통한 라우트 보호 (`middleware.ts`)
- shadcn/ui 컴포넌트 일체, 서버/클라이언트 Supabase 클라이언트 패턴

아래 명시된 **채팅 관련 기능(랜덤채팅, 방채팅, 메시지, 이미지 전송 등)은 DB 테이블부터 전부 없는 백지 상태**이며, 이번 MVP 개발의 대상이다. 단, PRD 원안의 "구글 로그인" 요구사항은 이미 구현된 이메일+OAuth 인증 스캐폴드를 그대로 활용하는 것으로 대체한다(§4.1 참고).

## 1. 제품 개요

### 1.1 제품 정의

수다온은 로그인 없이 바로 시작하는 1:1 랜덤채팅과, 로그인 후 이용하는 다인원 방채팅을 제공하는 반응형 웹 채팅 서비스다. 핵심 목표는 사용자가 복잡한 절차 없이 빠르게 대화를 시작하도록 하는 것이다.

### 1.2 MVP 목표

- 비로그인 사용자의 랜덤채팅 진입 장벽을 최소화한다.
- 회원에게 방 생성·입장·강퇴가 가능한 기본 방채팅을 제공한다.
- 텍스트와 이미지 전송을 모바일과 PC에서 지원한다.
- 서비스 반응을 확인한 후 광고 수익화로 확장한다.

### 1.3 포함 및 제외 범위

| 구분 | 내용 |
|---|---|
| 포함 | 로그인(이메일/OAuth), 프로필, 계정 탈퇴, 익명 랜덤채팅, 방채팅, 텍스트·이미지 전송, 비밀번호방, 강퇴, 닉네임 기반 사용자 검색 |
| 제외 | 친구·쪽지, 음성·영상, 읽음 표시, 푸시 알림, 유료 기능, 추천 알고리즘 |

## 3. 핵심 사용자 흐름

### 3.1 게스트 랜덤채팅

1. 홈에서 "랜덤채팅 시작"을 선택한다.
2. 임시 ID를 발급받고 매칭 대기열에 들어간다.
3. 상대가 매칭되면 1:1 채팅 화면으로 이동한다.
4. 텍스트·이미지를 전송하고 종료 또는 재매칭을 선택한다.

### 3.2 로그인 및 프로필

1. 로그인(이메일 또는 OAuth)을 진행한다.
2. 최초 로그인 시 닉네임을 입력한다(기존 `setup-profile` 플로우 재사용).
3. 저장 후 방채팅을 이용하며 프로필은 이후 수정하거나 계정을 탈퇴할 수 있다.

### 3.3 방채팅

1. 누구나 방 목록을 조회한다.
2. 입장 또는 방 만들기 선택 시 로그인을 확인한다.
3. 회원은 제목·최대 인원·비밀번호를 설정해 방을 만든다.
4. 방 안에서 대화하고 방장은 참여자를 강퇴할 수 있다.

### 3.4 사용자 검색

1. 로그인 사용자가 별도의 "사용자 검색" 화면에서 닉네임을 입력한다.
2. 닉네임이 일치·유사한 회원 목록과 각 사용자의 온라인 여부(현재 로그인 상태)를 확인한다.
3. 검색 결과에서 프로필을 조회한다.

### 3.5 주요 화면

| 화면 | 핵심 구성 |
|---|---|
| 홈 | 랜덤채팅 시작, 채팅방 둘러보기 |
| 로그인 | 이메일/OAuth 로그인 (기존 구현 재사용) |
| 프로필 | 닉네임, 사진, 계정 탈퇴 (기존 구현 확장) |
| 매칭 대기 | 진행 상태, 취소 |
| 랜덤채팅 | 메시지, 이미지, 종료·재매칭 |
| 방 목록 | 검색/분류, 방 카드, 방 만들기 |
| 방 생성 | 제목, 인원, 공개/비밀번호 |
| 방채팅 | 메시지, 이미지, 참여자, 강퇴 |
| 사용자 검색 | 닉네임 검색창, 결과 목록(닉네임, 온라인 여부), 프로필 조회 |

## 4. 기능 요구사항

### 4.1 로그인 및 프로필

| ID | 요구사항 | 비고 |
|---|---|---|
| AUTH-01 | 이메일 또는 OAuth로 로그인·로그아웃한다. | 기존 구현 재사용 |
| AUTH-02 | 로그인 사용자는 확인 절차 후 계정을 탈퇴할 수 있다. | 신규 구현 필요 |
| PRO-01 | 최초 로그인 시 닉네임은 필수로 저장한다. | 기존 구현 재사용 |
| PRO-02 | 프로필을 조회하고 수정할 수 있다. | 기존 구현 재사용 |

### 4.2 랜덤채팅

| ID | 요구사항 |
|---|---|
| RND-01 | 로그인하지 않아도 랜덤채팅을 시작할 수 있다. |
| RND-02 | 한 사용자는 동시에 하나의 대기 또는 채팅 세션만 가진다. |
| RND-03 | 서버 또는 DB 트랜잭션으로 중복 매칭을 방지한다. |
| RND-04 | 텍스트와 이미지 1장을 전송한다. |
| RND-05 | 매칭 취소, 대화 종료, 재매칭을 제공한다. |

### 4.3 완료 조건

**랜덤채팅 완료 기준**: 서로 다른 두 브라우저가 로그인 없이 매칭되고, 실시간 텍스트와 이미지 전송 후 정상적으로 대화를 종료할 수 있어야 한다.

### 4.4 사용자 검색

| ID | 요구사항 |
|---|---|
| SEARCH-01 | 로그인 사용자만 닉네임으로 다른 사용자를 검색할 수 있다. |
| SEARCH-02 | 검색 결과에 닉네임과 현재 온라인(로그인) 여부를 표시한다. |
| SEARCH-03 | 게스트(익명 사용자)는 검색 대상에서 제외한다. |

**사용자 검색 완료 기준**: 로그인 사용자가 닉네임 일부만으로 대상 회원을 찾고, 그 회원의 현재 온라인 여부를 정확히 확인할 수 있어야 한다.

## 5. 방채팅 요구사항

| ID | 요구사항 |
|---|---|
| ROOM-01 | 모든 사용자가 방 목록을 조회할 수 있다. |
| ROOM-02 | 방 입장과 생성은 로그인 사용자만 가능하다. |
| ROOM-03 | 방 제목, 최대 인원, 공개 여부, 비밀번호를 설정한다. |
| ROOM-04 | 정원 초과 입장을 차단한다. |
| ROOM-05 | 텍스트와 이미지 1장을 전송한다. |
| ROOM-06 | 방장만 참여자를 강퇴할 수 있다. |
| ROOM-07 | 강퇴된 사용자는 해당 방에 다시 입장할 수 없다. |

### 5.1 핵심 정책

| 구분 | 정책 |
|---|---|
| 이미지 | JPG·PNG·WEBP, 최대 5MB |
| 비밀번호 | 원문이 아닌 해시로 저장 |
| 권한 | 현재 세션 또는 방 참여자만 메시지 조회·전송 |
| 강퇴 | 방장 권한을 서버에서 재검증 |
| 매칭 이탈 | 취소·연결 종료 시 대기열에서 제거 |

### 5.2 방채팅 완료 조건

**방채팅 완료 기준**: 회원이 공개방·비밀번호방을 생성하고 입장할 수 있으며, 정원 제한과 방장 강퇴 권한이 올바르게 적용되어야 한다.

## 6. UI/UX 및 기술 구성

### 6.1 UI/UX 원칙

- 화이트톤을 기본으로 하고 강조색은 한 가지 계열만 사용한다.
- 모바일 우선 반응형 UI로 구성한다.
- 홈의 핵심 버튼은 "랜덤채팅 시작"과 "채팅방 둘러보기"로 단순화한다.
- 채팅 입력창과 전송 버튼은 화면 하단에서 쉽게 조작할 수 있게 한다.
- 강퇴·대화 종료·계정 탈퇴 등 주의가 필요한 기능은 일반 버튼과 명확히 구분한다.

### 6.2 반응형 레이아웃

| 환경 | 구성 |
|---|---|
| 모바일 | 단일 열, 메뉴 축소, 참여자 목록은 별도 패널 |
| PC | 좌측 메뉴 + 중앙 콘텐츠 + 선택적 우측 정보 패널 |

### 6.3 기술 구성

| 영역 | 기술 | 역할 |
|---|---|---|
| 프론트 | Next.js (App Router) | 화면, Server Action/Route Handler |
| 인증 | Supabase Auth | 이메일/OAuth 로그인 (기존 구현) |
| DB | Supabase PostgreSQL | 회원·방·메시지·매칭 |
| 실시간 | Supabase Realtime | 실시간 메시지 |
| 파일 | Supabase Storage | 프로필·채팅 이미지 |
| 배포 | Vercel | Next.js 운영 배포 |

### 6.4 최소 데이터 모델 (개요)

| 테이블 | 용도 |
|---|---|
| profiles | 회원 프로필 (기존 구현) |
| random_queue / random_sessions | 랜덤 매칭 대기 및 세션 (신규) |
| rooms / room_members | 방 정보 및 참여자 (신규) |
| messages | 텍스트·이미지 메시지 (신규) |

> 상세 컬럼/제약조건/RLS 정책은 `DB_SCHEMA.md`에서 정의한다.

**구현 원칙**: 실시간 메시지는 Supabase Realtime을 구독하고, 매칭·강퇴·비밀번호 검증은 서버 액션 또는 PostgreSQL 함수에서 처리한다.

## 7. 보안 및 출시 기준

### 7.1 최소 보안 요구사항

- Supabase RLS로 세션·방 참여자만 메시지에 접근하게 한다.
- 서버 전용 키는 브라우저에 노출하지 않는다.
- 계정 탈퇴 요청은 로그인 상태와 사용자 본인을 서버에서 재검증한 후 처리한다.
- 이미지 형식·용량을 검증하고 UUID 파일명으로 저장한다.
- 메시지 전송과 방 생성에 기본 요청 횟수 제한을 적용한다.
- 매칭·방 입장·강퇴 권한은 서버에서 재검증한다.

### 7.2 MVP 출시 수용 기준

| 시나리오 | 완료 조건 |
|---|---|
| 게스트 랜덤채팅 | 로그인 없이 매칭·텍스트·이미지·종료 가능 |
| 회원 프로필 | 로그인 후 저장·수정 가능 |
| 계정 탈퇴 | 로그인 사용자가 확인 절차 후 탈퇴하고 다시 로그인할 수 없음 |
| 방 생성/입장 | 공개방·비밀번호방 및 정원 제한 동작 |
| 방장 권한 | 일반 회원의 강퇴 요청은 거부 |
| 권한 보호 | 비참여 사용자의 메시지 접근 차단 |
| 반응형 | 모바일과 PC에서 주요 화면이 겹치거나 잘리지 않음 |
| 배포 | Vercel에서 Auth·DB·Realtime·Storage 정상 연결 |
| 사용자 검색 | 로그인 사용자가 닉네임으로 회원을 찾고 온라인 여부를 확인, 게스트는 검색 불가 |

### 7.3 개발 순서 (개요)

1. 문서화: PRD → ROADMAP → ARCHITECTURE → DB_SCHEMA → DEVELOPMENT_PLAN
2. 방 목록·방 생성·텍스트 방채팅
3. 사용자 검색
4. 랜덤 매칭·텍스트 랜덤채팅
5. 이미지 전송
6. 강퇴·계정 탈퇴·권한 검증
7. 반응형 점검과 Vercel 배포

> 세부 일정과 마일스톤은 `ROADMAP.md`에서 정의한다.

### 7.4 후속 검토 (MVP 이후)

- 광고 배치 및 수익화
- 운영자 관리 화면
- 관심사 기반 매칭
- 친구·쪽지·알림
- 콘텐츠 자동 검수

**출시 전 결정 필요**: 이용 가능 연령, 개인정보 보관 기간, 금지 콘텐츠, 계정 탈퇴 시 데이터 처리 방식, 광고 도입 시점을 운영 정책으로 확정한다.
